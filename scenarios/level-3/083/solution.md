# Solution · 083

## Diagnosis supported by supplied evidence

A configuration change modifies a replacement-triggering property.

## Investigate

Inspect the full saved plan, resource schema behavior, state address, and intended rename.

Correlate timestamps and recent changes. A similar symptom in a real environment can have a different cause.

## Recovery

Stop the apply; preserve the existing database and choose a reviewed non-destructive migration or configuration correction.

## Verify

A fresh reviewed plan contains no unintended replacement.

## Prevent recurrence

Review destructive plans and protect critical resources with layered controls.

## Interview follow-ups

- What evidence would invalidate this diagnosis?
- What availability or data risk does the repair introduce?
- How would you roll back if verification fails?
- What would you tell the incident commander in 60 seconds?
