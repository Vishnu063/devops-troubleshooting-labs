# Ecosystem acceptance scenarios

These ten scenarios map to the existing catalog/runners; mappings are starting points, not claims that every optional metric/connector has been exercised. Read the target lab README before injection. All setup/injection/cleanup is restricted to an explicitly owned Docker container or `kind-devops-labs` namespace. Never run a failure scenario on production, a customer cluster or the pharmacy application.

The concrete lightweight acceptance driver is `ecosystem/acceptance.py`. It builds/runs CloudLaunch's separate stateless sample, uses real Prometheus + Blackbox + Alertmanager, sends an authenticated alert into Ops Pilot, collects real container evidence, proves execution is refused before approval, approves/applies the existing restart, verifies HTTP/metrics/alert resolution, and exports the correlated audit report. Requires explicit opt-in and local Unix Docker. It does not require Jenkins, Kubernetes, Grafana, a model or cloud credentials. A live Jenkins deployment, cluster/GitOps rollouts, host-resource pressure rules, Grafana provisioning and optional K8sGPT require their own acceptance; scenario metadata is not that evidence.

Use the existing `lab.py` / native runner instructions for Kind and other fixtures. Their existing solution and reset/down commands remain authoritative. The new driver imports the shared Triage package and CloudLaunch deploy/cleanup code instead of duplicating deployment or remediation logic. Its output identifies each passed stage, unresolved gate and measured process/container resources where available. The Ops Pilot CI runs it only on a disposable runner and uploads the evidence. See Ops Pilot's `docs/ECOSYSTEM.md` for exact repository refs and current results.
